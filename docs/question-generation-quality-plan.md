# 問題生成の品質改善・実装計画

作成日：2026-09-30。2026-10-01に評価セット・品質審査・題材変更・少数完了（第0・第1段階）を実装し、既存Cloudflare経路の本番へ反映。HTTPのLANアクセスに対応するフロント修正も含む。学習項目の事前抽出（第2段階）と利用者フィードバック（第3段階）は今後の計画。検証結果は verification.md を参照。

## 目標

「資料に存在する情報」から「学ぶ価値がある情報」を選び、意味のある問題だけを問題バンクへ保存する。

- 資料名、ページ、図の目盛りの本数など、資料の識別・表示だけを問う問題を除く。
- 重要な数値、名称、定義、規則を直接思い出す問題は採用する。
- 正解・解説の根拠を資料内で確認できることを採用条件にする。
- 問題数の指定は生成の目標とし、品質を満たす題材が不足したら少ない問数で終了する。

## 現行処理と問題点

`generation_sources()` → 原則4行の出題範囲 → `select_source_units()` → 範囲ごとに1問生成 → 形式・正解露出・完全一致重複のチェック → 保存。

1. `has_substantive_source_text()` は長さ・語句・数値の有無を見ており、重要度は評価しない。
2. `extract_testable_facts()` は文の分類であり、学習項目の選別ではない。
3. 未使用の場所を優先するため、重要な本文より未出題の注記が選ばれる場合がある。
4. `review_question()` と `metadata_trivia_reason()` は生成時の保存判定に使われていない。
5. 再生成は同じ断片で行われる。題材自体が不適切でも別範囲へ移れない。
6. 直接生成ジョブは目標問数までループする。0問・少数を返すだけでは終わらない可能性がある。
7. 現行レビューには「資料の文をそのまま再生するだけなら棄却」という広い条件があり、そのまま接続すると有用な直接想起まで落とす可能性がある。

## 採用基準

難易度と学習価値を別に扱う。簡単な暗記でも、重要な知識を確認できれば採用する。

| 観点 | 採用条件 | 棄却例 |
| --- | --- | --- |
| 学習価値 | 資料の主要内容、必要な手続き、重要な指標・目標などを確認できる | 入力資料の書類名、目盛りの本数、装飾の色 |
| 根拠 | 正解と解説が、引用した資料の記述から確認できる | 資料に説明のない増減理由の推測 |
| 成立性 | 対象・年度・単位・条件が明確で、正答が定まる | どの事業の数値か分からない質問 |
| 問い方 | 重要な概念・事実を確認できる | 接続詞など任意の語だけを隠した穴埋め |

「書類名」「目盛り」という単語だけで棄却しない。業務手順書にある必須提出書類名や、グラフ読解を教える資料の軸・目盛りの意味は採用候補。資料名・位置情報を問題内の前提として示すことも許容する。

棄却理由は機械的に扱えるコードと具体的な説明で返す。

- `document_metadata`：入力資料の名前・場所の識別だけを問う。
- `visual_trivia`：図表の外観・表示要素の数を問う。
- `low_learning_value`：資料の主題や必要な知識に結びつかない細部。
- `unsupported_answer`：正解・解説を根拠本文で確認できない。
- `ambiguous_target`：対象や条件が不明確。
- `arbitrary_cloze`：重要性のない語を隠しただけ。
- `answer_leak`：問題文に正答が露出している。

学習価値・根拠・成立性のどれかが不合格なら保存しない。総合点で他の欠陥を相殺しない。

## 第0段階：評価材料を用意する

変更前に、小規模な評価セットを作る。

- 統合報告書、規程・業務手順、研修資料の3種類を含める。
- 不要な問題20件以上、有用な問題20件以上を出典と対で用意する。架空の資料で自動テスト用のケースを作り、実資料は開発用のローカル評価で使う。
- 資料名と必須提出書類名、目盛りの本数と軸の意味、不要な数値と重要な目標値を対にする。
- 良問・悪問・判定が分かれる問題を区別し、曖昧な例を確定ラベルへ無理に入れない。
- 現行生成の採用率、不要問題率、生成時間、API呼び出し数を同じ資料で記録する。

生成モデルと同じモデルの自己評価だけで改善を判定せず、人の評価を基準にする。

成果物：評価ケース、判定ガイド、変更前の評価記録。

## 第1段階：保存前の品質審査・題材変更・少数完了

根本改善に先立ち、現在の生成経路へ品質審査を接続する。審査だけの導入で停止・補充処理を後回しにしない。

### 1. 品質審査

`providers.py` の `review_question()` を採用基準に合わせて変更する。

- 入力：問題、サーバーが解決した根拠本文、資料の主題・学習目的。
- 出力：`acceptable`、各観点の判定、棄却理由コード、具体的な理由。
- 生成側の「この問題は重要」という自己説明を採用の根拠にしない。別のAPI呼び出しで問題と根拠を審査する。
- 審査のJSON欠損・不正は採用扱いにしない。通信障害と品質による棄却は別の結果にする。
- 正規表現は明白なケースを早く落とす補助にする。単語だけで有用な問題を排除しない。
- MockProviderは決定的なルールとテスト用応答を使い、意味品質を保証したように表示しない。

`main.py` では、形式・正解露出チェックの後、保存前に審査する。既存の重複判定と保存直前のトランザクション内の照合を維持する。

根拠IDが無効な場合、入力範囲を自動的に根拠へ付け替えて通す現在の処理も見直し、修正対象にする。モデルが返したIDは入力の許可リストと照合する。正しいIDだけでも根拠の妥当性は保証されないため、本文との審査も行う。

### 2. 再生成と題材変更

- 表現・曖昧さ・正答露出の問題：理由を渡して同じ題材から再生成する。
- 題材自体の価値が低い、根拠が不足：別の範囲へ移る。
- 初期値として同じ題材の作り直しは最大2回、候補生成総数は要求問数の3倍までとする。20問なら最大60候補。補充バッチごとではなくジョブ全体で予算を管理する。
- 棄却済み題材と候補をジョブ中に記録し、同じ候補へ戻り続けない。
- 候補が尽きる、または予算に達した時点で終了する。目標問数へ届かないことを理由に基準を下げない。

これらの上限は評価で調整する初期値であり、最適値が確定したものではない。

### 3. 少数完了のAPI・保存仕様

生成結果へ次の情報を追加する。

- `requested_count`：要求問数。
- `accepted_count`：実際の採用問数。
- `rejected_count`：棄却した候補数。
- `stop_reason`：`target_reached`、`candidate_exhausted`、`attempt_limit`。

セットの `question_count` は実保存数にする。`requested_count` と品質審査の集計も保存する。`used_source_locations` へ登録するのは採用問題の根拠だけ。棄却を使用済み問題と混同しない。

ジョブは既存の `queued/running/complete/failed` に `partial` を追加する。

- 全問採用：`complete`。
- 題材不足や上限到達で1問以上採用：`partial`。
- 0問で題材不足：`partial`、セットは作らず説明を表示。
- API障害など処理そのものの失敗：`failed`。保存済みバッチは残す。

現在の `total/completed` は直接生成では問数、レシピ生成ではセット数なので、この意味を勝手に変えない。共通の要求問数・採用問数を追加し、レシピ生成でも不足を表示できるようにする。

`run_direct_generation_job()` の補充ループは `stop_reason` で終了できるよう変更する。成功した少数バッチはセットと問題をまとめて保存し、API障害で審査が終わらなかったバッチは保存しない。`completed` を要求数で上書きする現在の完了処理を修正する。

レシピ生成では大問ごとの所属を維持し、空の大問を作らず、実際の小問数を保存する。再生成は元の大問番号から独立して採番しないよう既存画面の扱いも確認する。

### 4. 画面

- 実行中：「問題を作成中」「品質を確認中」など現在の段階と採用数を表示。
- 少数完了：「20問中14問を作成しました。学習に適した題材が不足したため終了しました」。
- 0問：「この範囲では学習に適した問題を作成できませんでした」。
- `partial` を終端状態としてポーリングを止め、保存済み問題一覧を更新する。
- 内部の棄却コードやAPI呼び出し数は通常画面に出さない。

主な変更先：`question_quality.py`、`providers.py`、`main.py`、`models.py`、`frontend/src/types.ts`、`frontend/src/main.tsx`。

完了条件：書類名・目盛り本数の候補が保存されず、有用な暗記問題が通る。0問・少数完了でループが終わり、採用数と保存数と表示が一致する。

## 第2段階：学習項目を先に選ぶ生成へ切り替える

生成経路を次へ変更する。

`資料の文脈ブロック → 学習項目候補の抽出 → 重要度と出題履歴で選択 → 問題生成 → 品質審査 → 保存`

### 1. 文脈ブロックと根拠位置を分ける

現在の4行の範囲は根拠位置を指す用途に使えるが、出題内容を決める唯一の単位にはしない。

- 段落、見出しと本文、表のタイトル・ヘッダー・行・注記をまとまりとして読む。
- PDFの読み順が不明確な場合は、無理に意味のまとまりを断定せずページ内の広い文脈を使う。
- ページをまたぐ説明には、必要な隣接範囲を追加する。
- モデル入力用の参照キーと、実際のページ・行・セル位置の対応をサーバー側で保持する。
- 複数範囲が必要な問いには複数の根拠を認め、現在の「source_keyを1つだけ」に限定する指示を改める。
- 抽出テキストから読み取れない図表は出題対象外にする。原本を確認しない推測で値・傾向・因果を補わない。

初期実装は既存抽出本文を使う。新しい画像解析・図表認識基盤は別の拡張とする。

### 2. 学習項目のデータ

追加モデル `LearningObjective` の案：

| フィールド | 用途 |
| --- | --- |
| `id` | 同じ項目を再選択・追跡する安定したID |
| `material_id` / `material_version` | 対象資料と版 |
| `topic` / `proposition` | 主題と資料が述べる具体的事実 |
| `kind` | 定義、規則、目標、比較、因果、手順など |
| `importance` | core / supporting。出題不適切な情報は候補にしない |
| `learning_value_reason` | 学習上重要と判断した理由 |
| `allowed_question_goals` | remember / explain / apply / compare / judge / sequence |
| `evidence_refs` | 引用本文と内部参照キー |
| `extraction_version` / `source_hash` | 再抽出の必要性を判断する情報 |

重要度は資料の主題に照らして判断する。統合報告書なら戦略・業績指標・リスク・ガバナンス、規程なら対象・条件・期限・例外・手続きなどを優先する。資料種別が確定できなければ、本文から主題を抽出する。

モデルが返した根拠キーと引用はサーバーで入力へ照合し、根拠が存在しない候補は登録しない。抽出は上限のあるバッチで資料全体に分散させ、冒頭だけで候補枠を使い切らない。

既存のJSONエンティティ保存方式で `learning_objectives` を追加できる。資料ID・版・本文ハッシュ・抽出ルール版をキャッシュキーにし、資料編集時は再抽出する。旧資料も初回生成時に抽出し、再アップロードは必要としない。資料削除時には対応する候補キャッシュを削除する。

### 3. 題材の選択

- 重要度を優先し、その中で未出題の学習項目と話題の分散を考慮する。
- 場所の未使用だけを最優先にしない。
- 同じ項目でも、重要な目標値・条件・理由など異なる問い方を許容する。
- 既存問題の概念・正解・問いの目的を参考にし、似た概念というだけで一律棄却しない。
- 品質棄却と既出による回避を別に管理する。特定形式で失敗した項目を、全形式で永久に禁止しない。
- 問題には `learning_objective_id` と品質ルール版を追加し、採用した題材を追跡できるようにする。

`extract_testable_facts()` は補助情報として残せるが、学習項目の選別の代わりにはしない。

主な変更先：新規 `learning_objectives.py`、`models.py`、`providers.py`、`main.py`、根拠位置の処理、資料更新・削除処理。

完了条件：題材に重要な理由と有効な根拠があり、図表と説明の分断で問題の意味が失われない。資料編集後に古い候補から生成しない。

## 第3段階：任意の利用者フィードバック

最初のリリースには必須にしない。第1・第2段階の評価後に追加する。

- 問題バンクに「学習に不要」「根拠が不明」「対象が曖昧」などの報告操作を設ける。
- 報告は問題を自動削除せず、品質基準の改善と次回の題材選びに使う。
- 完全削除時には、問題文をフィードバック内へ残さない。保存するなら理由コードなど最小限の情報にする。
- 個人の好みを全資料共通の禁止に広げず、資料と学習項目の文脈に限定する。

## テスト・品質評価

自動テストでは、意味品質そのものをモックで保証したことにしない。処理の契約と保存の安全性を確認する。

1. 棄却候補は問題バンクに保存されず、採用候補だけ保存される。
2. 表現上の不備は同じ題材を修正し、低価値な題材は別の題材へ移る。
3. 全候補棄却・候補枯渇・予算到達でジョブが終了する。
4. 直接生成・レシピ・再生成のすべてに同じ品質基準が適用される。
5. 不正なレビュー応答やAPI障害を、品質棄却や採用として扱わない。
6. 根拠ID不正・引用不一致・複数根拠を検証する。
7. 部分完了と失敗で実際の保存数を表示し、画面更新後も状態を復元する。
8. 正解露出・重複・数値入力・根拠表示・演習・削除の既存機能が動く。
9. 資料の編集・削除で候補キャッシュが失効・消去される。

現在の「全範囲を未使用順に使う」テストは仕様変更に合わせて見直す。位置情報の正しさと重要項目の分散を検証し、重要性の低い全範囲から必ず出題することは要求しない。

実モデルの評価では同じ資料・形式・問数を使って複数回生成する。初期の合格目安は、確定した不要問題ケースの棄却率95%以上、有用なケースの採用率90%以上、主要項目のカバー率が変更前以上。小さな評価セットによる目安であり、全資料での保証ではない。特に書類名・目盛り本数の代表ケースが漏れた場合は、理由を確認してから採用判断をする。

生成時間、呼び出し数、補充率も計測する。学習項目の抽出はキャッシュし、審査は小規模バッチ化を検討する。バッチ審査は候補IDで対応を確認し、返っていない候補を合格にしない。モデルの変更は最初の改善には含めず、現行モデルで基準を評価する。

## 実装の分割と反映

1. 評価ケース・判定基準を作成する。
2. 第1段階をバックエンド・画面・テストまでまとめて実装する。
3. 評価セットと実資料で第1段階を検証する。
4. 第2段階の文脈ブロック・学習項目抽出・キャッシュを実装する。
5. 学習項目からの生成へ切り替え、根拠と出題履歴を検証する。
6. 品質・生成時間・費用を比較して初期値を調整する。
7. README、architecture、verificationを更新する。

既存資料・生成問題へ追加フィールドの既定値を設け、保存済みの問題を自動で再審査・削除しない。新しい生成に品質基準を適用する。旧版への切り戻し時には実行中ジョブを整理してから、アプリケーションと候補キャッシュの版を切り替える。

本番反映は検証後の別工程とし、既存のDocker・Gateway・監視方式を使用する。保存volumeを保持し、問題生成・少数完了・根拠表示・演習を確認する。本計画の作成ではデプロイを行わない。
